# REVIEW.md: TaskFlow review rulebook

What can break in this codebase. The Reviewer (`.claude/agents/reviewer.md`) checks
every PR against the invariants the path map assigns to the changed files. The
Implementer reads the same invariants before touching those files.

- **`block`**: a violation with a concrete failure scenario blocks the merge.
- **`flag`**: a violation is a comment, not a blocker.
- Symbols are checkable by name (`git grep`), so line numbers are left out on purpose.

This is the template's starting rulebook. The invariants below cover what the
template's own code relies on, so each one says *why* instead of citing evidence. A
project created from this template keeps the structure and grows its own
invariants from its history: every bug that reaches production adds or sharpens
one, with the commit that fixed it as *Evidence* (see "Keeping this file useful").

## What "broken" means here

TaskFlow stores users' lists and tasks. In order of damage:

1. **A user reads or changes another user's data** (a list or a task they do not
   own).
2. **Data lost or corrupted by a migration**, or a migration that does not apply on
   Postgres.
3. **An endpoint reachable without the API key or a verified session**, or a secret
   shipped to the browser.

When a diff can be read two ways, check the reading that would produce one of these.

## Invariants

### Data access

**T1 · block · Every user-owned row is scoped to the current user.** Services take
`user_id` and filter on it (`models.List.user_id == user_id`, or a join to `List` for
tasks), or call `verify_list_ownership` before writing. Routers pass
`current_user.id`, never an id from the request. An id that arrives in the path or
body (`list_id`, `task_id`) is checked against its owner before use, on update as
well as on create. A row the user does not own answers 404, the same as one that
does not exist.
*Why: nothing else enforces ownership. The middleware checks the API key, not who
owns a row.*

**T2 · block · Endpoints stay behind the API key and a verified user.** Routes depend
on `get_verified_user`, or on `get_current_user` only where an unverified user must
get in. `EXEMPT_PATHS` in `app/core/middleware/api_key.py` grows only for a route
that authenticates itself (such as a signed webhook), with the reason next to it.
*Why: `TESTING=1` switches the API-key middleware off, so no test notices an exempt
or unauthenticated route.*

**T3 · block · Auth tokens expire, are single-use, and do not leak accounts.**
Session JWTs carry `exp`. Reset tokens expire (`reset_token_expires`). Reset and
verification tokens are cleared once used (`reset_password`, `verify_email`).
`forgot_password` behaves the same whether or not the email exists. Response
schemas such as `UserResponse` never carry a password hash or a token, and logs
never print one.
*Why: each of these is a one-line change that tests rarely cover.*

### Schema and migrations

**T4 · block · Migrations apply on Postgres and reverse cleanly.** One Alembic head.
An autogenerated migration is reviewed by hand. `downgrade()` reverses `upgrade()`.
A new non-null column on a table that has rows gets a server default or a backfill.
*Why: tests run on SQLite, which ignores Postgres ENUM types and some constraints.
CI's `alembic upgrade head` against Postgres is the only check that a migration
applies, and nothing checks the downgrade.*

### Frontend

**T5 · block · The two API layers stay separate.** `apiFetch` (`lib/api-client.ts`)
is used only in route handlers under `app/api/**` and in server components. Client
components call `features/<domain>/api.ts`, which calls the Next.js routes under
`/api/...`, never the backend URL.
*Why: `apiFetch` is what adds the `x-api-key` header and the session cookie on the
server. A client-side call either fails or needs the key in the browser.*

**T6 · block · Nothing secret reaches the browser.** A `NEXT_PUBLIC_*` variable is
inlined into the client bundle of every client component that imports the module
reading it, so it never holds a secret. New secrets are read only in server code.
*Why: the value ships to every visitor.*

**T7 · block · Fields the frontend reads exist.** `next.config.mjs` ignores type
errors, so `pnpm build` passes with a wrong field name. Every property the diff
reads exists on its type in `lib/types.ts` and on the backend response schema. A
renamed or removed response field is updated on both sides in the same PR.
*Why: the build stays green while the page shows an empty or wrong value.*

### Config

**T8 · flag · Settings are typed, defaulted and documented.** New settings are fields
on `app.core.config.settings` with safe defaults, documented in `.env.example`. No
secret is hardcoded or logged.

## Path map

| Changed path | Invariants |
|---|---|
| `backend/app/domains/*/service.py`, `backend/app/domains/*/router.py` | T1 T2 |
| `backend/app/domains/auth/**`, `backend/app/core/security.py`, `backend/app/core/dependencies.py` | T2 T3 |
| `backend/app/core/middleware/**`, `backend/app/main.py`, `backend/app/api/**` | T2 |
| `backend/app/domains/*/schemas.py` | T3 T7 |
| `backend/alembic/**`, any `models.py` | T4 |
| `frontend/app/api/**`, `frontend/lib/api-client.ts`, `frontend/features/*/api.ts` | T5 |
| `frontend/lib/config.ts`, `frontend/next.config.mjs` | T6 |
| `frontend/**` | T7 |
| `backend/app/core/config.py`, any `.env.example` | T8 |

## Do not flag

- **Pre-existing patterns the PR doesn't introduce or worsen** (`datetime.utcnow()`,
  `class Config` instead of `ConfigDict`).
- **Tests on SQLite instead of Postgres**: by design (CLAUDE.md §3). Flag the
  specific T4 risk instead.
- **No frontend tests**: the frontend has no test framework yet (CLAUDE.md §3).
- **Style, naming and formatting**: ruff and eslint own them.

## Keeping this file useful

- **A bug reaches production** → its fix PR adds or sharpens an invariant here,
  with the commit as evidence.
- **The Reviewer raises a false positive** → add it to "Do not flag".
- An invariant must be checkable from a diff plus the surrounding code. If it can't
  be, it belongs in a design doc, not here.
- Rename or delete invariants only with the code they describe; keep IDs stable so
  old review comments still point somewhere.
- **A project created from this template** renames this file's title, picks its own
  ID prefix, and replaces the "What broken means here" list and the invariants as
  its own history arrives. Keep the structure: the Reviewer relies on the IDs,
  severities, path map and "Do not flag" list.
